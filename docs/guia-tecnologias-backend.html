Parte 1 — Conceptos

Qué es cada cosa y por qué

Primero lo esencial: entender el vocabulario y las tecnologías antes de mirar una sola línea de código.

⚠ Aclaración #1 — la confusión más común

Es NestJS, no Next.js

Se parecen por el nombre y muchísima gente los mezcla, pero viven en mundos distintos: uno es del backend y el otro del frontend.

✓ LO USAMOS
NestJS
Framework de backend (el servidor / la API). Es el nuestro.
✕ NO LO USAMOS
Next.js
Framework de frontend (interfaces con React). No está en el proyecto.

Cómo está montado

Las 3 capas del backend

Nada de esto vive solo: cada capa corre sobre la de abajo. Entender este orden es lo que más ayuda a que todo lo demás tenga sentido.

▲ corre sobre ▲

Node.js el motor (runtime) que ejecuta el código en el servidor La base de todo

La idea clave: Node.js no es un framework — es el entorno donde todo corre. NestJS, Express, Prisma… todos son librerías que viven dentro de Node. Es como el motor de un carro: sin él, las demás partes no arrancan.

El inventario

Todas las tecnologías, una por una

Agrupadas por para qué sirven. Cada tarjeta trae qué es y qué buscar para empezar a estudiarla.

Núcleo

Node.js
runtime
JavaScript nació para correr dentro del navegador. Node.js es el programa que lo saca de ahí y lo deja correr en un servidor, como cualquier lenguaje de backend. Es el "motor" que ejecuta nuestro código: cuando arrancamos el proyecto, es Node quien lo pone a andar. Todo lo demás (NestJS, Prisma…) son librerías que corren dentro de Node.
En AvisensEs la base de todo. Sin Node, nada del backend arranca.
NestJS
@nestjs/core
El framework que le da forma al backend. En vez de armar el servidor a mano, impone una estructura clara: el código se divide en módulos, y cada módulo tiene un controller (las rutas) y un service (la lógica). Usa "decoradores" —las líneas con @— para marcar qué es cada cosa. Es lo más importante de dominar del proyecto.
En AvisensCada recurso (granjas, sensores, mediciones…) es un módulo de NestJS.
TypeScript
lenguaje
Es JavaScript pero con "tipos": tú declaras que una variable es un número, un texto, etc. Así el editor te avisa de los errores mientras escribes, antes de correr el programa. En un proyecto grande evita muchísimos bugs tontos y hace el código más fácil de entender.
En AvisensTodo el backend está escrito en TypeScript.
Express
@nestjs/platform-express
Es la librería que realmente escucha las peticiones HTTP (cuando el navegador o el ESP32 le "hablan" al servidor) y manda las respuestas. Es muy popular pero minimalista. NestJS lo usa por debajo, así que casi nunca lo tocamos directo: trabajamos sobre NestJS y él se encarga de Express.
En AvisensEs el motor HTTP invisible que corre bajo NestJS.

Base de datos

Prisma ORM
@prisma/client
Un ORM es un traductor entre tu código y la base de datos. En vez de escribir SQL a mano, escribes prisma.granja.findMany() y Prisma genera el SQL por ti. Además, defines todas las tablas en un solo archivo (schema.prisma) y él se encarga de crearlas en la base de datos.
En AvisensEl schema.prisma define las tablas del modelo de datos (el MER).
PostgreSQL
vía Supabase
La base de datos relacional donde se guarda todo de forma permanente: usuarios, granjas, cada medición de los sensores… "Relacional" significa que los datos viven en tablas conectadas entre sí (una granja tiene galpones, un galpón tiene sensores). Supabase es un servicio que nos aloja esa base de datos en la nube, lista para usar.
En AvisensGuarda absolutamente todo; corre alojada en Supabase.

Seguridad y autenticación

JWT
@nestjs/jwt
Cuando un usuario inicia sesión, el servidor le entrega un token: una cadena firmada que prueba quién es. En cada petición siguiente, el usuario manda ese token en lugar de la contraseña, y el servidor lo verifica para saber quién es sin volver a consultar la base de datos. JWT significa JSON Web Token.
En AvisensProtege las rutas privadas; cada petición trae su token.
Passport
passport-jwt
Es la librería que se encarga de leer y validar esos tokens dentro de NestJS. Define la "estrategia" de autenticación: de dónde saca el token (de la cabecera de la petición), cómo lo verifica y a qué usuario representa. Trabaja de la mano con JWT.
En AvisensValida el token en cada ruta protegida (el JwtAuthGuard).
Bcrypt
bcrypt
Las contraseñas nunca se guardan tal cual. Bcrypt las convierte en un hash: un texto irreversible del que no se puede recuperar la contraseña original. Al iniciar sesión se comparan los hashes, no las contraseñas. Así, si alguien robara la base de datos, no vería ninguna clave real.
En AvisensHashea la contraseña de cada usuario antes de guardarla.
Helmet
helmet
Un middleware (código que se ejecuta antes de responder) que añade automáticamente varias cabeceras de seguridad a las respuestas HTTP. Esas cabeceras le indican al navegador cómo comportarse de forma segura y bloquean varios ataques web comunes. Se activa con una sola línea.
En AvisensSe activa al arrancar el servidor, en main.ts.
Throttler
@nestjs/throttler
Rate limiting: limita cuántas peticiones puede hacer una misma persona en un periodo de tiempo. Sirve para frenar abusos, ataques de fuerza bruta contra el login (probar mil contraseñas seguidas) o que alguien sature el servidor a punta de peticiones.
En AvisensProtege sobre todo el inicio de sesión.

Validación, documentación y config

class-validator
+ class-transformer
Validan los datos que entran a la API. En los DTOs pones decoradores (@IsString, @IsEmail, @Min…) y estas librerías revisan automáticamente que todo cumpla antes de que tu lógica lo toque. Si algo está mal, devuelven un error 400 solitas. class-transformer además convierte los datos al tipo correcto (ej. el "5" de la URL a número).
En AvisensCada DTO (como CreateGranjaDto) usa estos decoradores.
Swagger
@nestjs/swagger
Genera automáticamente una página web con la documentación de la API, a partir de tus controllers y DTOs. Ahí cualquiera puede ver todas las rutas, qué reciben y qué devuelven, y hasta probarlas en vivo desde el navegador, sin instalar nada.
En AvisensDisponible en /docs cuando el servidor corre.
Config + dotenv
@nestjs/config
Los secretos y configuraciones (la clave de la base de datos, los secretos de JWT…) no se escriben en el código: van en un archivo .env que no se sube al repositorio. Estas librerías leen ese archivo y ponen esos valores a disposición del código de forma segura.
En AvisensDATABASE_URL, JWT_SECRET, etc. viven en el .env.

Mini glosario

El programa que ejecuta el código. En nuestro caso, Node.js.
Framework
Un conjunto de reglas y herramientas que dan estructura al proyecto. NestJS es el nuestro.

Traductor entre el código y la base de datos. Prisma es nuestro ORM.

Parte 2 — Estructura y código

Cómo está armado y cómo se escribe

Ahora lo concreto: la organización de carpetas y pedacitos de código real del backend, explicados para que puedas mostrárselos al equipo.

La organización

Estructura de carpetas

Todo vive dentro de src/. La idea de fondo: un módulo por cada recurso (granjas, sensores, mediciones…), y una carpeta common/ con lo que se comparte entre todos.

avisens-backend/src

src/
├─ main.ts              // arranca el servidor (el punto de entrada)
├─ app.module.ts        // registra TODOS los modulos
├─ prisma/              // la conexion a la base de datos
├─ common/             // codigo compartido por todos los modulos
│  ├─ guards/          // login (JWT) y control de roles
│  ├─ acceso.ts         // la regla "cada quien maneja lo suyo"
│  └─ pagination/      // paginacion reutilizable
└─ modules/            // un modulo por cada recurso del sistema
   ├─ auth/            // login y tokens
   ├─ granjas/
   ├─ galpones/
   ├─ dispositivos/
   ├─ sensores/
   ├─ mediciones/
   └─ ...

El patrón que se repite

Cómo es un módulo por dentro

Todos los módulos siguen la misma estructura de 4 piezas. Si entiendes uno, los entiendes todos. Aquí el ejemplo de granjas:

modules/granjas

granjas/
├─ granjas.module.ts       // une las piezas
├─ granjas.controller.ts   // las rutas (HTTP)
├─ granjas.service.ts      // la logica de negocio
└─ dto/                    // validacion de los datos que entran
   ├─ create-granja.dto.ts
   └─ update-granja.dto.ts
module
Une el controller y el service, y registra el módulo en la aplicación.
controller
Define las rutas HTTP (GET, POST, PATCH…). Solo enruta — no tiene lógica.
service
La lógica de negocio: decide qué se puede hacer y habla con la base de datos.
dto/
El "molde" que valida los datos de entrada de cada ruta antes de procesarlos.

Qué pasa en cada petición

El viaje de una petición

Cuando llega una petición (por ejemplo POST /granjas), pasa por esta cadena en orden. Cada eslabón puede detenerla si algo falla:

1

Guards — ¿quién eres?

Revisan que traigas un token válido (login) y el rol correcto. Si no → error 401 o 403.

2

DTO — ¿los datos vienen bien?

Valida el cuerpo de la petición. Si un campo falta o es inválido → error 400.

3

Controller — enruta

Recibe la petición ya validada y llama al método correcto del service.

4

Service — la lógica

Aplica las reglas de negocio y el alcance por rol (un Propietario solo ve lo suyo).

5

Prisma — la base de datos

Lee o escribe en PostgreSQL y devuelve el resultado.

6

Respuesta

Vuelve al cliente como JSON, con su código de estado.

Código real, explicado

Los archivos, con código de verdad

Fragmentos reales del módulo granjas. Cada bloque trae el código y, debajo, la explicación de lo importante.

granjas.module.ts — une las piezas

@Module({
  controllers: [GranjasController],  // las rutas
  providers:   [GranjasService],     // la logica
})
export class GranjasModule {}
  • El @Module es como el "índice" del módulo: le dice a NestJS qué controller y qué service lo forman.
  • Es el archivo más corto, pero es el que conecta todo.

dto/create-granja.dto.ts — el molde que valida

export class CreateGranjaDto {
  @IsString()                 // debe ser texto
  nombre: string;             // obligatorio (no lleva ?)

  @IsNumber()
  @Min(-90) @Max(90)          // latitud valida entre -90 y 90
  @IsOptional()               // puede faltar
  latitud?: number;

  @IsInt()
  @IsOptional()
  propietario_id?: number;    // solo lo usa el Administrador
}
  • Un DTO define y valida los datos que entran. Los decoradores (@IsString, @Min…) hacen la validación automática.
  • Si alguien manda una latitud de 200, la API la rechaza sola (error 400) antes de tocar la lógica.
  • El ? marca los campos opcionales; los que no lo tienen son obligatorios.

granjas.controller.ts — las rutas

@UseGuards(JwtAuthGuard, RolesGuard)        // exige login + rol
@Roles(ROLES.ADMINISTRADOR, ROLES.PROPIETARIO)
@Controller('granjas')                      // ruta base: /granjas
export class GranjasController {
  constructor(private granjasService: GranjasService) {}

  @Post()                                   // POST /granjas
  crear(@Body() dto: CreateGranjaDto, @Req() req) {
    return this.granjasService.crear(dto, req.user);
  }

  @Get(':id')                               // GET /granjas/5
  obtener(@Param('id', ParseIntPipe) id: number, @Req() req) {
    return this.granjasService.obtener(id, req.user);
  }
}
  • El controller solo enruta: recibe la petición y delega en el service. No tiene lógica de negocio.
  • @UseGuards + @Roles protegen todas las rutas del controller a la vez.
  • @Body saca el cuerpo, @Param saca el id de la URL, @Req da acceso al usuario logueado. ParseIntPipe convierte el id de texto a número.

granjas.service.ts — la lógica y el alcance por rol

@Injectable()
export class GranjasService {
  constructor(private prisma: PrismaService) {}   // habla con la BD

  async listar(solicitante, { page, limit }) {
    // un Propietario SOLO ve sus granjas; un Admin las ve todas
    const where = esPropietario(solicitante)
      ? { propietario_id: solicitante.id }
      : undefined;

    return this.prisma.granja.findMany({ where, take: limit });
  }

  async obtener(id, solicitante) {
    const granja = await this.prisma.granja.findUnique({ where: { id } });
    if (!granja) throw new NotFoundException('Granja no encontrada');  // 404
    verificarDueno(solicitante, granja.propietario.id, 'No es tuya');  // 403
    return granja;
  }
}
  • Aquí sí vive la lógica. El service decide qué puede ver y hacer cada usuario.
  • El alcance por rol es la línea clave: si es Propietario, filtra por propietario_id; si es Admin, no filtra nada.
  • Lanza excepciones que NestJS traduce a códigos HTTP: NotFoundException → 404, ForbiddenException → 403.

common/acceso.ts — la regla de seguridad, en un solo lugar

export function esPropietario(solicitante) {
  return solicitante.rol === ROLES.PROPIETARIO;
}

export function verificarDueno(solicitante, propietarioId, mensaje) {
  // un Propietario no puede tocar lo que no es suyo
  if (esPropietario(solicitante) && propietarioId !== solicitante.id) {
    throw new ForbiddenException(mensaje);   // 403
  }
}
  • Estas dos funciones centralizan la regla más importante del sistema: "cada quien maneja lo suyo".
  • Se reutilizan en todos los módulos (granjas, galpones, dispositivos…). Un solo sitio, sin repetir la regla en cada archivo.

Cómo se prueba la API

De la ruta al JSON: dónde vive cada cosa

Al probar la API en Bruno (o Postman) siempre surgen tres preguntas: ¿dónde escribo los métodos?, ¿cuál es la ruta? y ¿qué JSON mando?. Cada una tiene su archivo — y entender esto es la mitad del trabajo.

1.Los métodos (POST, GET, DELETE…) viven en el controller

Cada método se marca con un decorador que indica su verbo HTTP. Lo que va dentro (:id, permanente) completa la ruta.

granjas.controller.ts

@Controller('granjas')          // ruta base: /granjas
export class GranjasController {
  @Post()                       // POST   /granjas
  @Get()                        // GET    /granjas
  @Get(':id')                   // GET    /granjas/5
  @Patch(':id')                 // PATCH  /granjas/5
  @Delete(':id')                // DELETE /granjas/5
}

2.La ruta = base + controller + método

Se arma juntando tres partes. Con el servidor corriendo en el puerto 3000, así quedan las URLs para Bruno:

AcciónVerboURL
CrearPOSThttp://localhost:3000/granjas
ListarGEThttp://localhost:3000/granjas
Ver unaGEThttp://localhost:3000/granjas/5
DesactivarDELETEhttp://localhost:3000/granjas/5
  • Truco: no hay que adivinar. Con el servidor corriendo, abre http://localhost:3000/docs (Swagger) y verás todas las rutas listadas solas, con su verbo y listas para probar.

3.El JSON que mandas lo define el DTO

Cada propiedad de la clase DTO es una clave del JSON. Las que llevan ? son opcionales; las demás, obligatorias.

dto/create-granja.dto.ts — define el molde del JSON

export class CreateGranjaDto {
  @IsString()        nombre: string;      // obligatorio
  @IsOptional()      direccion?: string;  // opcional
  @IsOptional()      latitud?: number;    // opcional
}

…entonces en Bruno mandas este JSON

{
  "nombre": "Granja La Esperanza",
  "direccion": "Vereda El Progreso km 4",
  "latitud": 6.1553
}
  • Si omites un campo obligatorio (como nombre), la API responde 400 sola, gracias a class-validator.
  • En resumen: controller = dónde y qué ruta · Swagger = dónde las ves · DTO = qué JSON mandas.

★ El resumen en una frase

El backend corre sobre Node.js, usando NestJS como framework (que se apoya en Express), con Prisma como ORM sobre PostgreSQL (Supabase), autenticación con JWT + Passport, contraseñas con Bcrypt, validación con class-validator y documentación con Swagger.
